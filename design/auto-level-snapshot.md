# P4 后续立项设计 · auto 价位「有状态快照」特性

> 状态：**设计立项（Design Proposal）** — 未实现，待评审
> 关联：`feat/p4`（贴脸阈值修复 + 架构澄清）、本仓 `scripts/verify-regressions.js` 测试 #12
> 依据：`lib/engine.js` `decideAction` / `lib/portrait.js` `deriveLevels`

---

## 0. 一句话结论

**可以立项，但应作为「可选增量」而非「必修缺陷」。** auto 画像的实时风控已由 `monitors` 系统承接；本特性的增量价值是补上"按波动率归一化的硬止损/目标位触发"。建议以**默认关闭的特性开关 + 前端持有状态、引擎保持纯函数**的方式落地，工程量中等。

---

## 1. 问题定义（为什么现有架构做不到）

### 1.1 现状
`decideAction` 对 auto 画像置空 L（`profile.auto ? {} : profile.levels`），因此 auto 不参与硬止损/目标位判定。

### 1.2 根因（已实测证实）
```
deriveLevels(ind) 用 ind.price 反推 → target1 = P + floor（或固定阻力位 R）
decideAction 每次分析重新调用 deriveLevels
⇒ 价格上行时 target1 同步上行，P >= target1 恒为 false
```
实测（价格 100→112，ATR 1，阻力位 108）：`aboveT1` **全程 false**。

**结论**：不是"贴脸阈值太小"的问题（那已在 feat/p4 修复），而是**派生价位与现价绑定、无法充当固定触发点**。要参与硬触发，必须先把价位**钉死在某个固定参考价上**。这就是"有状态快照"要解决的问题。

---

## 2. 设计目标与非目标

### 目标
- G1 auto 画像能对**固定**止损/目标位产生真实的价格触发（EXIT / TAKE_PROFIT）。
- G2 引擎保持**纯函数、无 I/O**（现有架构强约束：`lib/*` 会进浏览器产物，禁止 require Node 模块/读环境）。
- G3 默认**行为不变**（未开启时与现状字节一致），可灰度。
- G4 与 P3 口径披露一致：快照价位在 UI 明确标注来源，不冒充研报。

### 非目标
- N1 不引入服务端状态（本应用是静态前端 + 可选薄后端，优先 local 状态）。
- N2 不替代 `monitors`（趋势/MA/区间/布林等仍是 auto 风控主力）。
- N3 不做回测/历史快照归档。

---

## 3. 核心设计

### 3.1 锚点选择（决定一切）

| 方案 | 锚点 | 优点 | 缺点 |
|---|---|---|---|
| A | **前收盘价 `preClose`** | 确定性、人人一致、日内稳定、随交易日更新 | 隔夜跳空后价位需刷新 |
| B | 当日首次分析时现价（synthesis 价） | 贴近"今天开盘时的判断" | 不同用户/设备可能不同 → 不可复现 |
| C | 用户设定成本价 | 与持仓强相关 | 需用户输入，非普适 |

**推荐 A（前收盘价）**。理由：A 股 `preClose` 是公开、确定、每日更新一次的参考；用它反推的止损/目标位对所有用户一致、可复现、可测试。隔夜跳空超过阈值时快照失效并重算（见 3.4）。

### 3.2 数据契约（引擎侧，保持纯函数）

```js
// analyze(code, opts) —— opts 新增可选快照
opts.snapshot = {
  day: '2026-09-18',          // 锚定交易日
  refPrice: 12.34,            // 锚点价（preClose）
  levels: { entry:[lo,hi], stopLoss, hardStop, target1, target2 },
  atr: 0.21                   // 生成时的 ATR，用于失效判定
}
```

- 引擎**只消费**快照，不产生/不持久化。
- `decideAction` 取值优先级：`profile.levels`（研报） > `snapshot.levels`（auto，仅当 `profile.auto`） > `{}`（现状）。
- 未传 `opts.snapshot` 时行为与今天完全一致（G3）。

### 3.3 生成与持有（前端侧）

```
app.js 首次分析某标的（当日）：
  1. 取 quote.preClose 作为 refPrice
  2. 用「以 refPrice 为现价的合成 ind」调用约简版 deriveLevels → snapshot.levels
  3. 若 opts 开启快照：localStorage['sentry.snapshot.'+code] = {day, refPrice, levels, atr}
  4. 后续每 8s 轮询：读取快照 → 作为 opts.snapshot 传入 analyze
  5. 跨日 / 跳空超阈 / 手动刷新 → 重算快照
```

- **状态只在前端**，引擎纯净（G2）。
- `localStorage` 不可用（隐私模式/SSR）→ 静默降级为"不传快照"（= 现状），不报错。
- 键名含交易日，天然完成跨日失效。

### 3.4 失效与刷新规则

| 条件 | 动作 |
|---|---|
| `snapshot.day !== 当前交易日` | 重算 |
| `|现价 - refPrice| / refPrice > 跳空阈值`（建议 8%，与贴脸阈值同源）| 重算 |
| 手动刷新 / 复盘重开 | 重算 |
| 快照缺失 / 解析失败 | 降级为不传（现状） |

### 3.5 触发语义（decideAction）

复用现有硬性风控分支，仅把 L 的来源换成快照：
```
belowHard  = L.hardStop && P <= L.hardStop       → EXIT（无条件清仓）
belowStop  = L.stopLoss && P <= L.stopLoss       → EXIT（3 日内不收回则离场）
aboveT2    = L.target2 && P >= L.target2         → TAKE_PROFIT（再减 1/3）
aboveT1    = L.target1 && P >= L.target1         → TAKE_PROFIT（量缩减 1/3）
```
**必须在信号文案中标注「基于 {day} 快照价 {refPrice} 推算」**，与研报口径区分（G4）。

### 3.6 UI 口径披露（与 P3 衔接）

P3 已引入 `levelOrigin` / `levelLabels`。本特性新增一个来源态：
- `levelOrigin = 'report' | 'derived'` → 扩展为 `'report' | 'derived' | 'snapshot'`
- `levelLabels`：`研报` / `ATR反推` / **`ATR反推·快照(MM-DD)`**
- 快照过期或失效时，UI 显示"快照已刷新"提示条（复用现有 toast）。

## 4. 备选方案与取舍

| 方案 | 说明 | 取舍 |
|---|---|---|
| **S1 本设计（前端快照 + 引擎消费）** | 状态在前端，引擎纯函数 | ✅ 符合架构强约束；❌ 换设备/清缓存后快照重建（可接受）|
| S2 服务端快照 | 薄后端缓存 | 违背"静态可部署"；引入运维面 → 否 |
| S3 只用 monitors | 不加 ATR 止损/目标 | 零工程量，但少了"波动率归一化价位"这一维度 |
| S4 锚点改用 MA20/长均线 | 价位随均线缓慢移动 | 均线本身在动，仍非严格固定，且与 monitors 的 MA 判定重复 → 否 |

**推荐 S1**，并把 S3 作为"若评估认为 monitors 已足够"的默认状态（即特性默认关闭）。

---

## 5. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 跨日锚点跳变导致价位一次性跳空 | 用户困惑 | 明确"快照每日重建"；UI 提示刷新 |
| 跳空/除权除息使旧快照失真 | 错误触发 | 跳空阈值失效 + 提示 |
| localStorage 不可用 | 特性静默失效 | 降级为现状，无副作用 |
| 与研报价位口径混淆 | 误导 | 强制来源标注（P3 机制） |
| 误当作"auto 全量风控" | 过度信任 | 文档明确：仅补 ATR 止损/目标触发；趋势/区间仍由 monitors |

## 6. 实施拆分（若评审通过）

| 阶段 | 内容 | 验证 |
|---|---|---|
| E1 | 引擎：`analyze` 接收 `opts.snapshot`；`decideAction` 取值链扩展；信号文案标注 | 单测：注入快照后 aboveT1 可真实触发；不传时行为与现状一致（字节级回归） |
| E2 | 前端：快照生成/持有/失效/降级 + 来源徽标 | 确定性 fixture + 跨日/跳空用例 |
| E3 | 口径披露扩展（与 P3 合并显示） | DOM 断言 |
| E4 | 特性开关与灰度 + 文档 | CI 全绿；默认关闭 |

**关键验收**：E1 的单测必须包含"注入快照 → 价格触达 → 真触发"，与现状"不传快照 → 恒不触发"形成对照（即把测试 #12 从"证明做不到"升级为"证明加快照后做得到"）。

---

## 7. 待决问题（需产品/作者拍板）

1. **是否值得做**：若认为 `monitors` 已覆盖 auto 风控的主要价值，可**不做**本特性（S3）。这是最重要的一个决定。
2. 锚点确认前收盘价（方案 A）是否可接受。
3. 跳空阈值取值（建议 8%，与贴脸阈值同源）。
4. 快照是否需要"用户可手动刷新/清除"入口。
5. 是否需要把快照状态纳入 P3 的 `levelOrigin` 枚举（我倾向于：是）。
